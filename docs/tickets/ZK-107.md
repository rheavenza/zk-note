# ZK-107 — Web sync flow and deployment acceptance

State: BACKLOG
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/3
Target: `master`

## Objective

Make the web sync state truthful and verify the complete user path from a local vault to a second device through the configured server.

## Dependencies

ZK-104, ZK-105, and ZK-106.

## Acceptance criteria

1. The UI distinguishes local-only, unauthenticated, offline, pending, syncing, synced, error, and conflict states. A successful timestamp appears only after a completed server round trip.
2. The UI offers a clear link/upload action for an existing local vault and restore action for a new browser; destructive ambiguity requires an explicit recovery decision.
3. A browser can create a note offline, link and sync, then a second browser can restore and read it after unlock. Subsequent edits and deletions converge through guarded sync.
4. Two-browser stale edit and delete conflicts remain visible and recoverable. Reload and temporary network loss do not discard pending work.
5. Setup docs explain API origin, HTTPS/WebAuthn RP compatibility, browser storage, and the sync procedure without embedding private hostnames or addresses.

## Verification

Run `cd apps/web && npm run lint && npm run typecheck && npm test && npm run build`; run relevant Rust tests. Record browser-level evidence for first upload, second-device restore, offline retry, conflict, deletion, lock/unlock, and auth expiry against an RP-compatible test deployment. Confirm the server sees only ciphertext and permitted sync metadata.

## Artifacts and fallback

Update web README and provide redacted screenshots or a short screen recording plus test logs in the implementation PR. If the live deployment is unavailable, retain automated and local HTTPS end-to-end evidence and mark only the live smoke criterion pending; never present local-only state as server synchronized.
