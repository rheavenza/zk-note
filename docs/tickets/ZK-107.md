# ZK-107 — Web sync flow and deployment acceptance

State: DONE (PR open / review pending)
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/3
Target: `master`

## Objective

Make the web sync state truthful and verify the complete user path from a local vault to a second device through the configured server.

## Dependencies

ZK-104, ZK-105, and ZK-106.

## Acceptance criteria

1. The UI distinguishes local-only, unauthenticated, offline, pending, syncing, synced, error, and conflict states. A successful timestamp appears only after a completed server round trip.
2. The UI offers a clear link/upload action for an existing local vault and restore action for a new browser; destructive ambiguity requires an explicit recovery decision.
3. A browser can create a note offline, link and sync, then a second browser can restore and read it after unlock. Subsequent edits and deletions converge through guarded sync.
4. Two-browser stale edit and delete conflicts remain visible and recoverable. Reload and temporary network loss do not discard pending work.
5. Setup docs explain API origin, HTTPS/WebAuthn RP compatibility, browser storage, and the sync procedure without embedding private hostnames or addresses.

## Verification

Run `cd apps/web && npm run lint && npm run typecheck && npm test && npm run build`; run relevant Rust tests. Record browser-level evidence for first upload, second-device restore, offline retry, conflict, deletion, lock/unlock, and auth expiry against an RP-compatible test deployment. Confirm the server sees only ciphertext and permitted sync metadata.

## Artifacts and fallback

Update web README and provide redacted screenshots or a short screen recording plus test logs in the implementation PR. If the live deployment is unavailable, retain automated and local HTTPS end-to-end evidence and mark only the live smoke criterion pending; never present local-only state as server synchronized.

## Implementation summary

### Truthful sync UX (acceptance A)

`apps/web/src/context/SyncContext.tsx` now models nine states — `local only`,
`sign in to sync`, `not synced yet`, `offline`, `pending changes`, `syncing`,
`synced`, `error`, `conflict` — and derives them from facts rather than optimism:

- `synced` is reachable **only** when an authenticated adapter is wired up *and*
  the durable `last_sync_at` for the linked identity is set. Zero pending
  mutations alone can no longer produce it.
- `pending changes` requires a real upload target; an unlinked vault with local
  mutations reports `local only` instead of implying a server queue.
- The store reads sync state under the identity derived from the **persisted vault
  link** (not the transient session), so logout/expiry keep showing the vault's
  real last-sync time while disabling sync.
- `useSync()` without a provider returns a stable local-only context instead of
  claiming `synced`.

`apps/web/src/components/SyncStatusIndicator.tsx` renders the new states with a
per-state, zero-knowledge explanation, shows the pending count on the offline
badge, and `apps/web/src/components/MarkdownEditor.tsx` now says **Saved
locally** so local persistence is never confused with server synchronization.

### Link / restore integration (acceptance B)

Existing ZK-105 link/restore behavior is preserved. The account-scoped database,
explicit link action, non-destructive mismatch refusal, and restore-then-unlock
flow were verified end to end in a real browser.

### Real-browser acceptance suite (acceptance C, D, E, F, G)

`apps/web/e2e/` (Playwright + Chromium, opt-in HTTPS mode) drives the production
bundle against a real `zk-server`, using a virtual platform authenticator; two
isolated browser contexts share one account through the same passkey.

| File | Acceptance |
| :--- | :--- |
| `sync-truthfulness.spec.ts` | local-only vs linked-unauthenticated vs not-synced-yet vs pending vs synced; sign-out keeps notes |
| `two-browser.spec.ts` | restore on a second browser, A→B and B→A edit convergence, deletion convergence, no resurrection, mismatched-vault refusal |
| `offline-retry.spec.ts` | offline queue, reload durability, reconnect retry, lost-response replay (no duplicate revision), 401/429/5xx retryability with stable mutation ids |

| `zero-knowledge-evidence.spec.ts` | payload hygiene across bootstrap upload, push, pull, conflict, tombstone, and auth; lock/unlock performs no network I/O |

### Defects found and fixed (all blocked ZK-107 acceptance)

1. **`BrowserSyncAdapter` invoked native `fetch` as an object method**
   (`apps/web/src/sync/adapter.ts`). Chrome rejects that with *Illegal invocation*,
   which the adapter misreported as a network failure — so **no browser could ever
   complete a sync**. Node-based unit tests could not catch it because undici's
   `fetch` is not `this`-sensitive. Fixed by binding to the global object; a
   regression test injects a `this`-sensitive fake fetch.
2. **Conflicts never reached the UI** (`apps/web/src/context/ConflictContext.tsx`,
   `apps/web/src/App.tsx`). `ConflictProvider` was mounted *outside*
   `NotesProvider`, so `useNotes()` returned a fresh fallback object every render,
   recreating the `ConflictStore` each pass and discarding `activeConflicts` before
   it could render. Fixed by reordering the providers (Notes above Conflict) and
   making `handleResolved` stable via refs; the context fallbacks are now
   module-level constants.
3. **Pulled remote changes never appeared** (`apps/web/src/context/NotesContext.tsx`).
   A successful round trip did not refresh the note list, so a restored vault
   looked empty until a manual reload. Added a sync-completion reload that is
   skipped whenever local work is unpersisted (re-checked immediately before the
   in-memory notes are replaced), so a background pull can never clobber an edit
   in progress.

### Deployment smoke status

- **Local automated HTTPS browser evidence: PASS** — the full browser suite runs
  against `https://localhost` with WebAuthn RP ID `localhost` and a same-origin
  `/v1` proxy, which is the deployment topology.
- **Live staging smoke: PENDING (external dependency).** No operator staging
  origin or credentials are available in this environment, and none may be
  committed. The deployment checklist in
  [`docs/deployment-web-termux.md`](../../docs/deployment-web-termux.md) records
  the exact steps and configuration values to verify on the real origin. This is
  the only acceptance item not closed by this change; local behavior is never
  presented as live-server-verified.

### Known limitations

- Locked-vault pull (ciphertext pulled and persisted while locked) is asserted by
  the shared-core suite `apps/web/test/sync-engine.test.tsx`, not by the browser
  suite, because no UI control initiates a sync while the vault is locked.
- Playwright writes its trace/screenshot artifacts to the gitignored
  `apps/web/e2e-results/`.
- The evidence spec's generated report has run-specific string lengths and is
  therefore written to the gitignored output directory; the committed document is
  the stable, curated copy.
