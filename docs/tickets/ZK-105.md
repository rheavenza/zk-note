# ZK-105 — Safely link and restore encrypted vault bootstrap

State: BACKLOG
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/3
Target: `master`

## Objective

Connect an existing browser vault to an authenticated account and support restoring that encrypted vault bootstrap on another browser without losing local or remote data.

## Dependencies

ZK-104, existing vault bootstrap API, shared Rust/WASM vault envelope code, and browser encrypted storage.

## Acceptance criteria

1. First link uploads only the existing encrypted bootstrap envelope and allowed metadata. The server receives no passphrase, plaintext content, vault key, or recovery key.
2. A second browser can fetch the encrypted bootstrap and unlock it with the correct passphrase or recovery path.
3. Existing remote bootstrap, local vault, wrong-account state, and mismatched bootstrap each stop with an explicit non-destructive choice or error. No automatic replacement or reinitialization occurs.
4. Failed upload, lost response, refresh, and retry preserve the local vault and lead to a deterministic linked/unlinked state.
5. Bootstrap identity/association persists locally without storing plaintext secrets; sign-out does not erase encrypted local content.

## Verification

Run `cd apps/web && npm run lint && npm run typecheck && npm test && npm run build` and relevant vault/server protocol tests. Add tests for first upload, remote restore, duplicate response, mismatch, wrong account, wrong passphrase, and network interruption. Confirm server request fixtures contain ciphertext and permitted metadata only.

## Artifacts and fallback

Document the link/restore flow and capture redacted two-browser evidence. If remote bootstrap differs, preserve both sides and require an explicit recovery/export decision; never overwrite either side to make the test pass.
