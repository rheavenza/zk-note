# ZK-105 — Safely link and restore encrypted vault bootstrap

State: IMPLEMENTED (PR pending review)
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/3
Target: `master`

## Objective

Connect an existing browser vault to an authenticated account and support restoring that encrypted vault bootstrap on another browser without losing local or remote data.

## Dependencies

ZK-104, existing vault bootstrap API, shared Rust/WASM vault envelope code, and browser encrypted storage.

## Acceptance criteria

1. First link uploads only the existing encrypted bootstrap envelope and allowed metadata. The server receives no passphrase, plaintext content, vault key, or recovery key.
2. A second browser can fetch the encrypted bootstrap and unlock it with the correct passphrase or recovery path.
3. Existing remote bootstrap, local vault, wrong-account state, and mismatched bootstrap each stop with an explicit non-destructive choice or error. No automatic replacement or reinitialization occurs.
4. Failed upload, lost response, refresh, and retry preserve the local vault and lead to a deterministic linked/unlinked state.
5. Bootstrap identity/association persists locally without storing plaintext secrets; sign-out does not erase encrypted local content.

## Verification

Run `cd apps/web && npm run lint && npm run typecheck && npm test && npm run build` and relevant vault/server protocol tests. Add tests for first upload, remote restore, duplicate response, mismatch, wrong account, wrong passphrase, and network interruption. Confirm server request fixtures contain ciphertext and permitted metadata only.

## Artifacts and fallback

Document the link/restore flow and capture redacted two-browser evidence. If remote bootstrap differs, preserve both sides and require an explicit recovery/export decision; never overwrite either side to make the test pass.

## Implementation note

- Implemented safe vault linking and remote bootstrap restoration in `apps/web/src/auth/vault-link.ts`:
  - Typed models for `VaultBootstrapDto`, `KdfParamsDto`, `WrappedVaultKeyDto`, and `VaultLinkRecord`.
  - Canonical DTO conversion functions (`toVaultBootstrapDto`, `fromVaultBootstrapDto`) and field-by-field equality validation (`areBootstrapsEqual`).
  - Strict secret inspection helper (`assertNoPlaintextSecrets`) verifying no passphrases, raw keys, recovery phrases, or plaintext leak across the wire or into storage.
  - Persistent link storage (`readVaultLink`, `writeVaultLink`, `clearVaultLink`) storing only origin, account ID, and link timestamp in `zk_vault_link` localStorage.
  - Non-destructive `linkLocalVaultToAccount`: validates account status, checks existing remote bootstrap, uploads ciphertext envelope and allowed KDF/version metadata, and handles 409 idempotently if remote bootstrap matches local. Divergent remote vaults fail with `MismatchedVaultError`.
  - Non-destructive `restoreVaultFromAccount`: fails with `ExistingLocalVaultError` if an active local vault differs, fetches remote bootstrap, validates `crypto_version === 1`, writes bootstrap to `IndexedDbStorage`, and writes local link record.
- Integrated link state and `restoreFromRemote` into `apps/web/src/context/VaultContext.tsx`, and provided `useVaultOptional()` for components used across different provider contexts.
- Updated `apps/web/src/components/AuthControls.tsx` to display vault link status and provide `[Link vault to account]` and `[Restore vault from account]` actions with non-destructive error handling.
- Updated `apps/web/src/components/UnlockScreen.tsx` to embed auth controls, offer remote vault restoration when in `UNINITIALIZED` state with an active account, and show link status / wrong-account warnings when in `LOCKED` state.
- Added comprehensive automated test suite `apps/web/test/vault-link.test.tsx` verifying:
  - First link upload payload hygiene (zero plaintext, zero raw keys, permitted ciphertext only).
  - Idempotent 409 retry on identical bootstrap.
  - Rejection of mismatched remote vault (`MismatchedVaultError`).
  - Rejection when linking to a wrong/different account (`WrongAccountError`).
  - Network error safety preserving unlinked state.
  - Second browser remote bootstrap restore and association.
  - Local vault conflict detection preventing overwrites (`ExistingLocalVaultError`).
  - 404 missing remote vault error.
  - Full end-to-end multi-thread Web Worker restore and unlocking with both master passphrase and recovery phrase.
  - UI rendering in `AuthControls` and `UnlockScreen`.
- Addressed PR review findings (review comment 5361482564, 4140817981, 4140817986):
  1. Enforced persisted two-tuple identity `(serverOrigin, accountId)` on `linkLocalVaultToAccount` and `restoreVaultFromAccount` (`OriginMismatchError` and `WrongAccountError`), preventing silent re-binding or vault uploads to mismatched server origins.
  2. Enforced existing persisted link validation in `restoreVaultFromAccount` before fetching or modifying data, protecting both initialized and uninitialized states against cross-account/cross-server overwrite.
  3. Made storage writes observable and fail-closed across `writeVaultLink`, `clearVaultLink`, and `persistBootstrap`. `restoreFromRemote` and `setVaultLink` fail without transitioning state machine to success if persistence fails.
  4. Added deterministic unit/integration tests for server origin mismatch, wrong-account restore, and storage write failures (`setItem` throwing).
  5. Added web quality gates and build job to `.github/workflows/ci.yml` for independent GitHub Actions coverage.
  6. Made `readVaultLink()` fail closed on storage read exceptions (`STORAGE_ERROR`) and corrupted/malformed stored link records (`CORRUPT_VAULT_LINK` / `CorruptedVaultLinkError`), while strictly preserving key absence (`null`/`undefined`) as the only legitimate unlinked state. Guaranteed that `linkLocalVaultToAccount` and `restoreVaultFromAccount` fail closed before dispatching any network requests when storage read fails or link data is corrupted.
