# ZK-111 — Remote-safe native sync execution and CLI sync command

State: READY
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/14
Target: `master`
Dependencies: ZK-110

## Objective

Make native synchronization safe and usable over real Internet links without
freezing the TUI, while preserving the existing shared sync engine semantics.

## Current problem

The TUI currently awaits `perform_sync(...).await` inside the main UI loop.
The native sync HTTP adapter also lacks explicit bounded connect/request
timeouts. A stalled remote server can therefore make the full-screen interface
unresponsive.

The documentation also refers to `zk-note sync`, but current native CLI command
parsing does not expose an equivalent non-interactive command.

## Required implementation

1. Add explicit bounded connect and request timeouts to the native sync HTTP
   adapter. Configuration may use environment/CLI overrides, but defaults must be
   finite and documented.
2. Run TUI sync as a background async task, not inside rendering/input handling.
3. Preserve responsive navigation, lock/quit handling, and status rendering while
   sync is in flight.
4. Add operation-generation / identity guards so a late sync result from an old
   server/account/vault cannot update the current TUI state.
5. Define safe cancellation/shutdown behavior. Cancellation must not corrupt the
   durable cursor or silently drop pending mutations.
6. Reuse the existing `SyncEngine`; do not create a second sync state machine in
   the TUI.
7. Add a real `zk-note sync` CLI subcommand using the same non-printing client
   sync service.
8. Sync must validate the ZK-110 persisted vault link before contacting remote
   sync endpoints.
9. Preserve pull-before-push, CAS, idempotency, conflict and tombstone behavior.
10. Do not claim `Synced` after timeout/error/partial failure.

## TUI states

At minimum distinguish:

- idle;
- syncing;
- synced;
- offline/network timeout;
- unauthenticated/expired/revoked;
- pending local changes;
- conflict;
- server/account/vault mismatch;
- error.

The interface must remain responsive during a deliberately stalled server test.

## CLI behavior

`zk-note sync` should provide deterministic human-readable output and a stable
non-zero exit status on failure. If repository conventions support JSON output,
provide `--json` with a stable schema containing at least accepted/conflicted/
remaining counts and cursor information without secrets.

Do not add automatic background synchronization in this ticket unless explicitly
approved; the user-triggered `s` and `zk-note sync` flows remain the primary
actions.

## Required tests

- connect timeout;
- total/request timeout;
- dropped connection;
- 401/403 session failure;
- 429/5xx retryable failure;
- stalled server leaves TUI input/ticks responsive;
- lock while sync is in flight;
- quit/cancel while sync is in flight;
- stale result after account/server/vault identity switch is ignored;
- pending mutations survive timeout/cancellation;
- cursor advances only after durable pull persistence;
- CLI sync success/conflict/offline exit behavior;
- CLI and TUI share the same client sync service;
- existing sync regression suite remains green.

## Verification

Run Rust workspace gates, `zk-cli` tests, sync tests, synthetic PTY tests and a
real local server smoke with deliberate network stalls/faults.
