# ZK-110 — Native vault link, restore, account isolation, and replace-local-from-origin

State: READY
Priority: P0
Source: https://github.com/rheavenza/zk-note/issues/14
Target: `master`
Dependencies: ZK-109

## Objective

Make native CLI/TUI multi-device vault onboarding safe and explicit.

A local vault must be persistently bound to the exact server/account/vault
identity it synchronizes with. A second machine authenticated to the same account
must be able to restore the encrypted VaultBootstrap, unlock locally, pull the
same ciphertext vault, and then participate in guarded sync.

Also add an explicit destructive operation to discard the current local vault and
replace it from the authenticated server's canonical remote vault.

## Required identity model

Persist a native vault-link record binding at least:

- normalized server origin;
- account ID;
- stable vault identity/fingerprint derived from non-secret encrypted bootstrap
  identity/version data;
- link format version.

Authentication does not select local vault storage by itself. Sync must validate
the persisted link before any pull/push.

Fail closed on:

- wrong server origin;
- wrong account;
- corrupt link state;
- remote bootstrap mismatch;
- attempting to silently relink an existing local vault;
- changing authenticated account/server and pressing sync.

Offline access to an already linked encrypted local vault must remain available
without a currently valid server session.

## First-machine link flow

For an initialized local vault with no link:

1. Require an authenticated server account.
2. Inspect remote `GET /v1/vault/bootstrap`.
3. If no remote bootstrap exists, explicitly offer **Link and upload encrypted
   vault bootstrap**.
4. Upload only the existing encrypted `VaultBootstrap` and permitted metadata.
5. Persist the local vault link only after the server round trip succeeds.
6. Do not upload plaintext, vault passphrase, raw VaultKey, or recovery key.
7. A remote bootstrap that already exists and does not match must never be
   overwritten implicitly.

## Second-machine restore flow

For an authenticated machine with no local vault:

1. Fetch the remote encrypted VaultBootstrap.
2. Persist/stage it locally without treating authentication as vault unlock.
3. Ask for the vault passphrase or existing recovery flow locally.
4. Successfully unwrap/validate the same VaultKey locally.
5. Create a fresh local encrypted database.
6. Pull remote ciphertext from cursor 0.
7. Durably persist objects/tombstones before advancing cursor.
8. Persist the exact server/account/vault link.
9. Never send the passphrase or raw keys to the server.

Interrupted restore must be retryable without leaving a falsely linked or
half-initialized active vault.

## Replace local vault from server/origin

Provide both a TUI action and non-interactive CLI command for an explicitly
destructive reset, e.g. conceptually:

```
zk-note vault replace-from-server
```

Exact naming may follow repository conventions.

This operation means:

> Discard this machine's current local vault state and reconstruct it from the
> authenticated server's remote VaultBootstrap + ciphertext history/current
> objects.

It MUST NOT delete or reset the server-side vault.

### Destructive replacement contract

1. Verify an active authenticated session first.
2. Verify the remote encrypted bootstrap exists and is structurally valid.
3. Compare authenticated server/account against the existing local link and show
   the exact mismatch/target to the user.
4. Detect and prominently report:
   - pending local mutations;
   - in-flight mutations;
   - unresolved conflicts;
   - local changes not yet confirmed by the server.
5. Never push those pending/discarded mutations as part of replacement.
6. Require explicit destructive confirmation in the TUI. The CLI must require an
   explicit flag/typed confirmation suitable for scripts and must never default
   to destructive behavior.
7. Build the replacement in a staging location separate from active
   `vault.json` / `notes.db`.
8. Validate/unlock the staged bootstrap locally using vault passphrase/recovery.
9. Pull from cursor 0 into a fresh staged encrypted database.
10. Do not touch the active vault until staging, validation and pull complete.
11. Lock/scrub any active decrypted state before the swap.
12. Atomically or crash-safely switch the active vault/bootstrap/database/link to
    the staged version.
13. Only after the new local vault is committed, delete the old local encrypted
    vault/database/session state that is being replaced.
14. Preserve the server auth session and persistent device identity required for
    the operation.
15. Any failure before the committed swap leaves the original local vault usable.
16. Crash recovery must never produce a state that mixes bootstrap A with
    ciphertext DB B.

A backup/export option may be offered, but the required behavior is safe
destructive replacement, not mandatory retention of the old local vault.

## Multi-machine guarantees

Each machine has its own local SQLite database. Sharing `notes.db` via
NFS/Syncthing/cloud-drive synchronization is unsupported and should be documented.

Existing CAS, mutation idempotency, durable cursor, conflict preservation and
tombstone guarantees remain authoritative after restore.

## TUI behavior

Add clear states/actions for:

- local-only/unlinked vault;
- linked vault;
- remote vault available for restore;
- wrong account/server;
- bootstrap mismatch;
- restore in progress;
- destructive replace confirmation;
- pending/conflict discard warning;
- restore/replace failure without local data loss.

No destructive action may be bound to a single accidental keystroke.

## Required tests

At minimum:

- first-machine link/upload;
- link persistence and reload;
- wrong-account sync refusal;
- wrong-server sync refusal;
- corrupt-link fail closed;
- second-machine bootstrap restore;
- wrong passphrase leaves local state unchanged;
- interrupted bootstrap fetch;
- interrupted initial pull;
- restore from cursor 0 including tombstones;
- two isolated data dirs unlock/decrypt the same remote vault;
- destructive replacement with clean local state;
- replacement with pending mutations requires explicit discard;
- replacement with conflicts requires explicit discard;
- staging failure preserves original local vault;
- wrong passphrase during replacement preserves original local vault;
- crash/failure around swap cannot mix bootstrap/database generations;
- successful replacement removes old local vault state but preserves auth/device
  credentials;
- replacement never sends discarded pending mutations;
- zero plaintext/passphrase/raw-key network evidence.

## Verification

Run full Rust gates, CLI/TUI tests, sync/storage tests, and deterministic
two-client integration against a real local native server.

## Out of scope

- Replacing/deleting the remote server vault.
- Merging two unrelated vaults.
- Automatic account/server relinking.
- Sharing a local SQLite file between devices.

## Handoff

Open a PR from `work/ZK-110-native-vault-link-restore` to `master` and stop
for independent review. Include exact failure-injection evidence for the staged
replace-local path and exact tests proving account/server isolation.
