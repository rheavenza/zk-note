# ZK-108 — Username/password authentication alongside passkeys

State: READY
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/9
Target: `master`

## Objective

Add conventional username/password server-account authentication alongside the existing WebAuthn/passkey flow. The account password is strictly separate from the vault passphrase and must not grant the server any ability to decrypt vault content.

## Dependencies

ZK-104 session/origin handling, existing shared auth protocol, native Axum auth routes, Cloudflare Worker auth routes, and current device/session revocation behavior.

This ticket is independent from ZK-105/ZK-106 and must be implemented in a separate PR.

## Acceptance criteria

1. A user can register and sign in with username/password from the web UI, while passkey registration/login continues to work.
2. Username/password auth returns the existing session shape so protected vault/sync/device routes use the same bearer-session authorization path.
3. Password credentials are stored separately from vault bootstrap/KDF data. Raw passwords are never persisted or logged, and the vault passphrase is never accepted by account-auth endpoints.
4. Password verifiers use vetted Argon2id with unique random salts, versioned/encoded parameters, constant-time library verification, and explicit production parameters. Test-only faster parameters remain isolated to tests.
5. The native server and Cloudflare Worker expose compatible `POST /v1/auth/password/register` and `POST /v1/auth/password/login` contracts.
6. Append-only native and D1 migrations enforce unique normalized usernames. Existing migration files are not rewritten.
7. Login failures do not reveal whether the username or password was incorrect. Public password login has bounded brute-force protection on both backends.
8. Browser password fields are never written to localStorage/sessionStorage, URLs, logs, diagnostics, or sync/vault payloads. Only the existing origin-bound session is persisted after success.
9. Sign-out/session revocation semantics remain unchanged and fail visibly if server revocation cannot be confirmed.
10. An authenticated password account may enroll a passkey using the existing authenticated WebAuthn enrollment flow.
11. Account password authentication never uploads, links, replaces, or decrypts the local vault automatically.
12. If secure Argon2id parameters cannot run within the Cloudflare Worker runtime/resource budget, mark the task `BLOCKED / SPEC QUESTION`; do not silently weaken password hashing.

## Username/password policy

Unless an existing repository rule supersedes it:

- username: trimmed, case-insensitive canonical form, 3–64 characters, ASCII letters/digits plus `.`, `_`, and `-`;
- password: minimum 12 characters, maximum 256 UTF-8 bytes;
- no mandatory uppercase/symbol composition rules.

Document any intentional change to this policy.

## Implementation guidance

- Put shared request/response models in `zk-protocol`.
- Keep password hashing/verification in a server-only shared boundary, preferably `zk-server-auth`; do not import client vault crypto into server apps.
- Add a dedicated password-credential table keyed by account ID with a unique normalized username and encoded verifier.
- Reuse existing session issuance, device registration, expiration, authorization, and revocation code after credential verification.
- Extend `AuthContext` and the account control with separate username/password and passkey actions.
- Signing in still does not link/upload the local vault.
