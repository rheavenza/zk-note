# ZK-109 — SSH-key authentication for native CLI/TUI

State: READY
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/14
Target: `master`

## Objective

Allow the native `zk-note` CLI/TUI to authenticate to `zk-server` with an SSH key
without requiring a pre-existing browser/session token. SSH is an authentication
credential only: synchronization remains HTTPS over the existing `/v1/*` API.

The private key must never leave the client. After SSH proof succeeds, reuse the
existing account/session/device/revocation model and issue the same bearer-session
shape already consumed by native sync.

## Dependencies

- ZK-072 native device/session authentication.
- ADR-0006 server authentication verification.
- Existing native `zk-server` account/session/device persistence.
- Existing CLI/TUI account modal and secret-redaction rules.

## Required design

1. Add server-side SSH public-key credentials associated with account IDs.
2. Initial supported key type: `ssh-ed25519`.
3. Prefer `ssh-agent` / agent-protocol signing on the client. Do not read/export
   a private key when an agent-backed identity is available.
4. Optional direct identity-file support may be added only if encrypted OpenSSH
   key handling and local passphrase prompting remain safe and reviewable.
5. Do not expose port 22 and do not tunnel note synchronization through SSH.
6. Remote server URLs remain HTTPS-only under the existing URL validator.
7. Successful SSH authentication issues the same `SessionResponse` and device
   authorization semantics as existing passkey/session flows.

## Challenge protocol

Add versioned request/response models in `zk-protocol` and compatible native
server routes, conceptually:

- `POST /v1/auth/ssh/start`
- `POST /v1/auth/ssh/finish`

The exact serialized form may be adjusted during implementation, but the signed
message must be canonical and domain-separated, binding at least:

- protocol/domain string such as `zk-note-ssh-auth-v1`;
- server origin / audience;
- account or credential identity;
- local device ID;
- challenge ID;
- at least 256 bits of CSPRNG challenge material;
- expiry.

Challenges must be single-use, short-lived, and atomically consumed. Replay,
wrong-origin, wrong-account, wrong-device, expired, malformed, or unsupported-key
proofs fail closed.

Use a vetted SSH signature/parser implementation; do not implement Ed25519 or the
OpenSSH wire format manually.

## Account/key provisioning

Because this milestone does not depend on the web notes UI, provide an
operator-controlled native server command for first-account/bootstrap provisioning,
for example:

```
zk-server account create --ssh-key ~/.ssh/id_ed25519.pub
zk-server account add-ssh-key <account-id> ~/.ssh/laptop.pub
```

Exact command names may follow the existing server CLI architecture.

After an account has an authenticated session, normal key management should be
possible through authenticated API/CLI operations:

- list SSH credentials/fingerprints;
- add a new public key;
- revoke a public key.

Prefer one SSH key per machine so lost devices can be revoked independently.

Only public keys, stable fingerprints, labels, and required metadata are stored.
Raw private-key material must never be accepted by server endpoints.

## TUI/CLI UX

The TUI account modal should support SSH authentication without pasting an
existing bearer token.

The CLI should support a flow similar to:

```
zk-note login --server https://notes.example.com
```

If multiple suitable agent identities exist, offer a deterministic selection or
an explicit `--identity`/fingerprint selector. Never print private material or a
full session token.

After authentication the TUI should display the existing authenticated account
state and continue to use normal bearer sessions for sync.

## Security requirements

- Preserve SEC-001 through SEC-010.
- Vault passphrase and SSH credentials are independent.
- Never derive vault keys from SSH keys.
- Never send vault passphrase, VaultKey, note plaintext, or SSH private key to the
  authentication endpoints.
- Never log signed challenge bytes together with sensitive session material in a
  way that creates reusable credentials.
- Public-key lookup failures and bad signatures should not expose unnecessary
  account-enumeration information.
- Existing session expiration, logout, and device revocation semantics remain
  authoritative after SSH login.

## Persistence/migrations

Use append-only native SQLite migrations for SSH credentials and challenges.
Do not rewrite previous migrations.

At minimum enforce:

- stable credential ID/fingerprint;
- unique public key credential where appropriate;
- account ownership;
- revoked/active state;
- challenge purpose, expiry and one-time consumption.

## Required tests

Cover at least:

- supported Ed25519 public-key parsing;
- malformed/unsupported key rejection;
- unique key/fingerprint persistence;
- challenge randomness and TTL;
- challenge single-use/replay rejection;
- wrong account/device/origin rejection;
- valid signature -> existing session issuance;
- invalid signature -> no session;
- revoked key/device/session rejection;
- adding and revoking a second machine key;
- ssh-agent client signing with synthetic/test agent fixture;
- secret-redaction and Debug/error behavior;
- existing passkey/session authentication regression;
- no vault/passphrase/plaintext fields in SSH auth traffic.

## Verification

Run repository Rust gates, native server/auth tests, CLI tests, and the relevant
shared auth contract. Add deterministic local server integration coverage for the
full SSH start/sign/finish/session/status/revoke flow.

## Out of scope

- Username/password authentication.
- SSH daemon/port-22 deployment.
- Using SSH as the sync transport.
- Web-note UI work.
- Replacing the existing bearer session after authentication.

## Handoff

Open a PR from `work/ZK-109-ssh-auth` to `master` and stop for independent
review. Report exact base/head SHA, migrations, protocol shapes, supported key
types, challenge construction, agent behavior, tests, and known limitations.
