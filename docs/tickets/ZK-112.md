# ZK-112 — Remote native multi-machine acceptance and deployment

State: READY
Priority: P1
Source: https://github.com/rheavenza/zk-note/issues/14
Target: `master`
Dependencies: ZK-109, ZK-110, ZK-111

## Objective

Prove the terminal-first product works end to end across multiple isolated
machines/data directories through an HTTPS-accessible native `zk-server`, and
document a safe Internet deployment.

## Reference deployment

Document native `zk-server` bound to loopback behind HTTPS.

Reference personal/self-hosted topology:

```
TUI clients
    |
  HTTPS
    |
public hostname
    |
Cloudflare Tunnel
    |
127.0.0.1:8080
  zk-server
    |
 server.db
```

Cloudflare Tunnel is the reference convenience deployment, not a protocol
dependency. Nginx/Caddy/direct TLS remain valid alternatives.

Do not expose plain HTTP to remote clients and do not expose server port 8080
directly to the public Internet in the reference setup.

## Required acceptance scenario

Use two isolated native client data directories (or two disposable machines) and
a real native server.

1. Provision one account and two independent SSH public-key credentials.
2. Machine A authenticates with SSH key A.
3. Machine A initializes a vault, links it, uploads encrypted bootstrap and syncs.
4. Machine B authenticates with SSH key B to the same account.
5. Machine B has no local vault and restores from the server.
6. Machine B unlocks locally with the same vault passphrase/recovery material.
7. Both machines can read the same notes after sync.
8. A edit -> B pull converges.
9. B edit -> A pull converges.
10. Concurrent stale edits produce a visible recoverable conflict, not silent
    overwrite.
11. Delete-vs-edit produces the expected tombstone/conflict behavior.
12. Offline edits remain queued and retry after reconnect.
13. Restart/reload does not lose cursor, pending work, vault link or auth device
    identity.
14. Revoking Machine B's SSH credential/device/session prevents further remote
    access without affecting Machine A.
15. Wrong account/server link attempts fail closed.
16. Exercise **Replace local vault from server/origin**:
    - create divergent disposable local state on B;
    - confirm pending/conflict warning if applicable;
    - explicitly discard local state;
    - stage/fetch/unlock/pull remote vault;
    - verify B matches server/A afterward;
    - prove discarded mutations were not pushed.

## Network evidence

Capture redacted/asserting evidence that remote requests contain only:

- authentication challenge/signature/public credential metadata;
- bearer session token in the Authorization header;
- encrypted VaultBootstrap;
- opaque encrypted envelopes/blobs;
- permitted IDs/revisions/cursors/tombstone metadata.

Assert absence of:

- note title/body/tags/search text;
- vault passphrase;
- raw VaultKey/object keys;
- recovery key;
- SSH private key;
- plaintext attachment names/content beyond what current encrypted protocol permits.

Do not commit real credentials, hostnames requiring secrecy, tokens, or personal
note content.

## Deployment documentation

Document:

- persistent SQLite location and backup;
- loopback bind;
- Cloudflare Tunnel or TLS reverse-proxy example;
- HTTPS URL used by native clients;
- SSH account/key provisioning;
- first-device link;
- second-device restore;
- key/device/session revocation;
- replace-local-from-origin recovery;
- failure/retry expectations;
- how to migrate a client to a replacement machine;
- warning never to share `notes.db` itself between machines.

## Quality gates

Run all repository gates plus a scripted native two-client acceptance suite.
Where a public Internet smoke is unavailable in CI, keep a deterministic local
HTTPS reverse-proxy/tunnel-equivalent test and record the external smoke as a
manual acceptance item rather than claiming it ran.

## Completion

ZK-112 is DONE only when ZK-109 through ZK-111 are merged and this exact
multi-machine scenario passes without security-invariant exceptions.
